Trust boundary: the HTTP server. Every request field (path values, JSON body,

from another.

## Findings

### Finding 1: Any caller can delete any user's messages (no ownership check on DELETE) — `internal/handler/message.go:108`

- Severity: Medium
- Confidence: 0.85
- Category: access_control
- Description: `HandleDelete` deletes any message given only its ID
  (`DELETE FROM messages WHERE id = ?`, `internal/store/sqlite.go:147`). It
  does not check that the caller is the recipient or the sender. The UUIDv4
  IDs cannot be guessed, but that does not protect them, because
  `GET /api/messages/{address}` (`internal/handler/message.go:86`) returns
  every message ID for any recipient address with no authentication.
  Recipient addresses are wallet addresses and are public by nature. The API
  key does not stop this either: it is one shared secret, and in the default
  configuration (`api_key: ""`) it is disabled. Client-side encryption
  protects only confidentiality. It does nothing to stop a third party from
  destroying the ciphertext. No project documentation says that anonymous
  deletion of other users' messages is intended. The README documents the
  endpoint but not who may call it, so this is reported as a Finding and not
  as a Note.
- Exploit Scenario: An attacker who knows a target's wallet address `0xVictim`
  polls `GET /api/messages/0xVictim` and sends `DELETE /api/messages/<id>` for
  each result. Every message sent to the victim is removed before the
  victim's client fetches it, so the attacker can silently suppress all mail
  to that address. One script can do this for every address it can list.
  With `ttl_days: 0` ("forever" mode), deletion is the only way messages ever
  leave the store, so this attack is the only thing that removes them.
- Recommendation: Require proof of ownership for deletion. One option is to
  issue a random per-message deletion token from `crypto/rand` in the
  `POST /api/messages` response (or give it to the recipient through the
  payload). Store only its hash, and require the token on `DELETE`, comparing
  with `subtle.ConstantTimeCompare`. Another option is to require a signature
  from the recipient's wallet key over `(message id, timestamp)`. At a
  minimum, stop returning IDs for deletion to unauthenticated readers, and
  document the current behaviour in the README if it is intended.

### Finding 2: Failed API-key attempts are never rate-limited (auth runs before the limiter) — `cmd/relay/main.go:106`

- Severity: Low
- Confidence: 0.7
- Category: authentication
- Description: The middleware chain is CORS → `APIKeyAuth` → `RateLimiter` →
  router (`cmd/relay/main.go:105-108`). A request with a wrong `X-API-Key` gets
  its 401 from `APIKeyAuth` before `rl.allow()` is ever called, so failed
  guesses are not counted or throttled. Nothing enforces a minimum length or
  entropy for `security.api_key` (`internal/config/config.go:188-205`
  validates the port, TTL, payload size, rate limit, and origins, but not the
  key). An operator who picks a short or dictionary key has no online-guessing
  protection. This needs a weak operator-chosen key to be exploitable, which
  is why the severity is Low and the confidence 0.7.
- Exploit Scenario: A private relay is set up with `api_key: "relay2026"`. An
  attacker sends a high-rate dictionary attack against
  `POST /api/messages` with varying `X-API-Key` values. Every attempt is
  answered with no throttling, and the key is recovered. The attacker then has
  full client access to the private relay.
- Recommendation: Apply rate limiting before authentication, or keep a separate
  failed-auth counter keyed by client IP inside `APIKeyAuth`. Moving the
  limiter outward only helps if the client IP cannot be spoofed.
  `extractIP` (`internal/middleware/ratelimit.go:118-144`) trusts
  client-supplied `X-Forwarded-For` / `X-Real-IP` without any trusted-proxy
  check, so an attacker can rotate that header to get a fresh bucket on every
  request. Use `r.RemoteAddr` by default, and honour forwarding headers only
  when the direct peer is in a configured trusted-proxy list. Also reject, or
  warn loudly about, API keys shorter than about 32 characters in
  `Config.Validate`.

## Notes

### Note 1: Anyone can list all messages and metadata for any address — `internal/handler/message.go:86`

- Category: design-tradeoff
- Observation: `GET /api/messages/{address}` returns every non-expired message
  for the address, including `id`, `to`, `from`, `payload`, `createdAt`, and
  `expiresAt`. It requires no proof that the caller owns the address. Any
  client (anyone at all when no API key is set) can read every recipient's
  ciphertext and the communication metadata: who messaged whom, when, and how
  often.
- Rationale: The README (line 63) and `AGENTS.md` describe the server as a
  "dumb encrypted mailbox" that "never sees plaintext — all
  encryption/decryption happens client-side". `internal/model/message.go:5-7`
  says the relay is "intentionally 'dumb'". Payload confidentiality is
  deliberately handled by client-side encryption, so returning ciphertext by
  public address is part of the design. The metadata exposure (`to`/`from`
  graph and timing) is **not** covered by that encryption. Operators should
  know that this metadata is effectively public on an open relay, and the
  README could say so.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or
  traced at runtime, so timing-dependent, load-dependent, or
  infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a
  calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety
  guardrails built into some models can cause a real vulnerability to be
  softened, generalized, or left out rather than reported in exploit-level
  detail, and training-data bias can make some vulnerability classes easier
  for a model to recognize than others. Treat this report as a floor on what a
  full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability
  tied to a very recently disclosed CVE or library advisory may not be
  recognized as such.

**Review-specific limitations**

- The ThruBox Client SDK was not available. The `from` field in
  `POST /api/messages` is stored exactly as the client supplies it, with no
  authentication (`internal/model/message.go:25-35`), so any caller can claim
  any sender address. Whether this is exploitable depends on whether clients
  trust `from` or verify sender identity cryptographically inside the payload.
  That could not be checked, so it is not reported as a finding.
- Deployment topology was not available. It is unknown whether production
  relays sit behind a reverse proxy that overwrites `X-Forwarded-For`. The
  trust in that header is discussed only as it bears on Finding 2. Rate-limit
  bypass as a standalone resource-exhaustion issue is outside this skill's
  scope.
- Third-party dependency source (`mattn/go-sqlite3`, `google/uuid`,
  `yaml.v3`) was not reviewed. Dependency versions were not checked against
  advisories.
- Test files (`*_test.go`) and CI workflows under `.github/workflows/` were not
  reviewed for vulnerabilities.
